# Hosted terminal permissions

ORCA polls hosted panes on its existing four-second liveness cycle. This is independent of the 90-second transcript suspicion fallback. It reads only the visible screen, recognizes bounded Claude permission menus and Codex shell/MCP menus, and creates an identified escalation. Workspace trust remains a manual terminal action because it has no once scope.

CAPCOM must review the mission and the current escalation context before deciding. Call `answer_agent` with the current `escalation_id`, `answer: "allow"` (once only) or `answer: "deny"`, and a concrete `basis`. Detection is not authorization. Permission answers cannot be remembered. The older unbound `permit` command now refuses and directs callers to the identified escalation.

The collector claims the request before awaiting I/O, checks the agent UUID, session, session name, pane ID/PID and hash of the current request/options, and checks the visible request again immediately before delivery. Selection highlighting is excluded from the hash. Raw arguments are not exported as escalation context: tool/executable names and known operation fields are retained; other values require terminal review. The hash includes the unredacted request locally so redaction does not collapse different requests.

Only the numbered once option or Escape is sent, targeted to the observed pane ID. No Enter, session approval, global approval, sandbox change, policy change, agent relaunch or automatic approval is involved. The existing tmux `send-keys -c ''` fix remains in both delivery paths. A tmux delivery lock serializes competing collectors; a stale lock fails closed and requires terminal review. A pane option retains the attempted fingerprint across collector reloads/reconnects. Repeated requests with an identical fingerprint are conservatively refused even if they represent a later identical operation; finish those manually. New fingerprints produce new escalations and retire old ones. Stale IDs and concurrent duplicate answers cannot send another key.

## Evidence and limits

- `requested`: detected and available for a decision.
- `pending`: a response was requested; it is **not** proof of delivery, approval, execution or success. The interrupt stays open and its answer buttons are disabled. Uncertain delivery is not retried.
- `confirmed`: the same pane visibly returned to an ordinary CLI input (including the measured Codex placeholder) after a response request. This confirms **dialog closure only**, not which actor answered, which decision the CLI accepted, or whether the tool succeeded. The resolution text says this explicitly.
- A disappearing, changed or unreadable dialog does not establish tool success. Changed/disappeared requests are withdrawn with an unconfirmed outcome; unreadable panes remain pending until observation is possible.

Native verification on Codex 0.153.4 (shell and MCP) and Claude Code 2.1.263 established that the numbered shortcut **submits immediately**, including after moving selection away from the once option. No Enter is needed for these supported dialogs. Escape cancels. ORCA therefore uses one guarded key, without a second confirmation that could land on a replacement prompt. If a future layout remains open, it stays pending and requires terminal review rather than an unverified Enter. No native CLI approvals were exercised against production agents.

Terminal capture and key delivery are not an atomic native approval API. A human or the CLI can change state in the final interval between the last capture and `send-keys`; identical replacement dialogs without an observed gap are also indistinguishable. The implementation detects observable changes and minimizes this interval, but cannot promise transactional approval semantics. A quoted dialog rendered exactly like a live menu at the bottom is similarly indistinguishable; ordinary transcript echoes followed by output/input are rejected. Truncated/unknown menus fail closed. Native request IDs and responses would be needed to remove these limits; this change does not migrate hosted terminals.
